Poniżej konkretna propozycja zmodyfikowanego fragmentu oferty, zgodna z instrukcją naprawy.

> – [link 1] – aplikacja do zarządzania zleceniami serwisowymi; Java 17, Spring Boot 3, React 18, PostgreSQL; zakres: role, zamówienia, raporty.
> – [link 2] – wewnętrzny panel operacyjny dla logistyki; Spring Boot, React, PostgreSQL; zakres: przydzielanie zadań, historia zmian, widok mobilny.

### Wariant B — jeśli autor nie ma żadnego portfolio

Zamiast formułki wpisać:

> „Nie posiadam publicznego portfolio do wglądu. Uczciwie o tym piszę. Moje doświadczenie techniczne obejmuje:
> – Java / Spring Boot: [liczba] lat, m.in. [konkretne moduły, np. REST API, Spring Security, JPA/Hibernate, kolejki, schedulery].
> – React: [liczba] lat, m.in. [hooks, state management, integracja z API, responsywność].
> – PostgreSQL: [liczba] lat, m.in. [modelowanie, indeksy, migracje, optymalizacja zapytań].
> Propozycje weryfikacji:
> 1) Krótkie płatne zadanie próbne (np. 8–16 h) — na przykład implementacja jednego ekranu z Figmy plus endpointu w Spring Boot z zapisem do PostgreSQL.
> 2) Rozmowa techniczna z Waszym deweloperem / CTO.
> 3) Referencje od poprzednich klientów — mogę podać kontakt po podpisaniu NDA.”

### Uwagi weryfikacyjne do obu wariantów

1. **Wariant A** wymaga, by linki faktycznie istniały i były sprawdzalne — inaczej wprowadza klienta w błąd.
2. **Wariant B** jest bezpieczniejszy reputacyjnie, ale wciąż wymaga podania **konkretnych** lat i obszarów, nie ogólników.
3. W obu wariantach zalecane jest dodanie **płatnego zadania próbnego** jako alternatywy — to standardowy mechanizm redukcji ryzyka po stronie klienta, gdy brak portfolio.
